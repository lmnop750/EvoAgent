# STAR 法则：项目经历与实习经历编写指南

> 用途：后续编写、修改项目经历与实习经历，以及准备对应的面试讲述。
> 来源：用户提供的 5 张“高于人力／GAOYUHR”职场 STAR 法则图片。
> 说明：本文是要点归纳与写作延伸，不是图片逐字转录。图片中的案例与数据仅用于理解表达方法，不属于用户的真实经历。本文不改动已有简历。

## 1. 核心原则

STAR 的目的，是把“做过什么”讲成一条清楚、可信的因果链：

**在什么背景下，承担什么任务，采取什么行动，取得什么结果。**

“做得好”与“说得清”同样重要。好的经历描述应让读者看清问题、个人责任、解决方法和成果，而不只是看到技术名词或工作清单。

## 2. 图片中的 STAR 四要素

| 要素 | 要回答的问题 | 写作重点 |
|---|---|---|
| S — Situation（情境） | 什么时间、什么场景、什么背景？涉及哪些人？遇到什么问题？ | 简短交代关键背景和困难，让读者理解为什么要做这件事。 |
| T — Task（任务） | 要完成什么？目标和要求是什么？我的角色与职责是什么？ | 明确个人责任、目标和约束，区分团队任务与自己的任务。 |
| A — Action（行动） | 具体做了什么？采取哪些措施？克服什么困难？ | 展示关键步骤、思考、选择和执行过程，而不是只说“努力完成”。 |
| R — Result（结果） | 最终取得什么成果？产生什么影响？有哪些数据？学到了什么？ | 用可核实的数据或具体交付物说明结果，必要时补充经验沉淀。 |

S 与 T 的区别：S 说明“当时存在什么问题”，T 说明“我被要求或主动承担解决哪部分问题”。

A 与 R 的区别：A 说明“用了什么方法”，R 说明“方法带来了什么可验证变化”。“引入缓存”是行动，“重复请求减少”才是结果，后者仍需证据支持。

## 3. 从图片案例提炼的方法

以下数字均为图片示例，不可直接移植到个人简历。

### 3.1 销售方案：从任务压力到具体交付

- S：客户临时要求在 3 天内修改方案，打乱原定安排。
- T：独立负责修改，并按期交付符合要求的版本。
- A：明确核心需求、安排优先级、同步修改稿并确认方向。
- R：按时交付，图片以客户满意度 95% 和后续合作说明成果。

可迁移的方法：写清期限与责任，再说明如何确保交付。技术简历应突出决策和解决方法，不把加班时长当作核心能力证据。

### 3.2 面试案例：从“部门不配合”到协作机制

- S：项目涉及 4 个部门，信息不同步、交接节点不明确，进度落后原计划 15%。
- T：承担核心协调职责，在 1 周内梳理障碍，保障活动按期上线。
- A：沟通负责人、归纳问题、建立同步机制，明确任务节点、责任人与验收标准。
- R：协作障碍得到解决，项目按期上线，并沉淀标准流程模板。

可迁移的方法：不要停留在抱怨或“反复催进度”，而要说明建立了什么机制。图片这一案例的 T 段也包含行动描述；正式写作时可将具体措施归入 A，使职责与行动更清楚。

### 3.3 工作汇报：从“做了活动”到有依据的方案

- S：竞品降价后，产品销量下滑 15%。
- T：制定推广方案，改善销量。
- A：分析竞品与自身优势，组织功能体验、合作测评并优化详情页。
- R：图片以季度销量提升 20%、新增 3000 个精准用户说明成果。

可迁移的方法：把“发现问题 → 分析原因 → 选择方案 → 验证效果”连起来。技术经历同样需要交代为什么采用某个方案，而不只是列出用了哪些框架。

### 3.4 绩效总结：从“挽回客户”到问题解决闭环

- S：客户因服务响应慢提出终止合作。
- T：负责挽回客户。
- A：沟通诉求、制定专属方案、承诺响应时间并定期同步进度。
- R：图片以继续合作、推荐 2 个新客户、年度合作金额提升 30% 说明结果。

可迁移的方法：结果既可以是业务指标，也可以是流程、工具或可复用规范的沉淀，但需说明个人行动与成果之间的联系。

## 4. 用于技术简历的写法（延伸规则）

### 4.1 项目整体交代 S/T，亮点重点写 A/R

简历不必在每条前显式写出 S、T、A、R。推荐结构：

- 项目名称、角色、时间：说明经历身份和范围。
- 项目背景／简介：用 1–2 句话说明场景、核心问题和系统目标。
- 技术栈：列出与实际实现相关的主要技术，不代替行动描述。
- 核心亮点：每条围绕一个问题，写清个人行动和可验证结果。

背景集中写，避免每条反复介绍项目；每个亮点尽量能独立回答“为什么做、怎么做、做成了什么”。

### 4.2 单条经历的表达公式

```text
针对【问题/约束】，负责【职责/目标】，通过【关键方案与个人行动】，实现【可验证结果】。
```

压缩版本：

```text
【能力标题】针对【具体问题】，设计/实现/优化【技术机制】，经【验证方式】确认【结果或边界】。
```

不必机械填满每个槽位。如果职责已由上文说明，可以省略重复的“负责”；如果没有可信指标，就写交付能力和验证结果，不硬凑百分比。

### 4.3 行动描述要体现技术判断

优先说明：

1. 识别到什么瓶颈或风险。
2. 为什么选择该方案，有哪些限制或取舍。
3. 自己具体实现了什么模块、机制或验证方法。
4. 如何确认结果，失败时如何处理。

可使用“设计、实现、定位、重构、集成、验证、优化”等动词。“主导、独立负责、从零搭建”仅在职责事实支持时使用。

避免只写：“使用 Python、Redis、Docker 完成系统开发。”

可改为：“针对重复请求导致的并发处理冲突，实现任务认领与版本校验，通过并发测试验证重复请求被拒绝。”该句为写法示例，使用前仍须确认对应实现与证据。

## 5. 项目经历模板

### 5.1 先整理事实

```markdown
项目名称：
角色：
起止时间：
项目性质：课程 / 个人 / 开源复现与改进 / 团队研发 / 企业项目

S 情境：面向谁？原流程有什么问题？为什么值得解决？
T 任务：我承担哪些模块？目标、预算、时间与安全约束是什么？
A 行动：关键方案是什么？我具体实现什么？与原有方案相比改了哪里？
R 结果：交付了什么？如何验证？数据来源与适用范围是什么？

个人贡献：
团队或原项目已有能力：
证据位置：代码 / 测试 / 报告 / 演示 / 验收记录
尚未完成或未验证的部分：
```

### 5.2 压缩为简历

```markdown
【项目名称】｜【角色】｜【起止时间】

项目背景：针对【场景】中的【核心问题】，开发/改进【系统】，支持【核心目标】。
技术栈：【与实际工作相关的技术】

- 【核心能力一】：针对【问题】，实现【关键机制】，通过【验证方式】达到【结果】。
- 【核心能力二】：承担【模块】，采用【方法与取舍】，完成【交付/改善】。
- 【评测与工程化】：构建【测试或评测方案】，在【数据和环境范围】内验证【结果与边界】。
```

条目数量随版面与事实调整，不为凑数量拆分同一贡献，也不把多个不相关问题硬塞入一条。

## 6. 实习经历模板

实习经历更需突出实际职责、业务场景、交付对象和协作边界，不能把团队总成果全部写成个人成果。

```markdown
【公司/机构】｜【部门与岗位】｜【起止时间】｜【地点，如需要】

- 【业务/研发任务】：面向【使用方】的【问题】，负责【具体模块或工作范围】，通过【行动】完成【可验证交付】。
- 【技术改进】：针对【已有流程瓶颈】，定位【原因】并实现【方案】，在【测试/业务口径】下取得【结果】。
- 【协作与沉淀】：与【相关团队】明确【接口/数据/验收要求】，交付【工具、流程或文档】，支持【已确认的用途】。
```

研究类实习可围绕数据整理、实验复现、训练评估、工具开发和研究产出展开，不需要虚构客户、营收或线上规模。实验完成、论文录用、专利申请和专利授权是不同状态，应准确区分。

## 7. 结果与数据的使用规范

### 7.1 量化前先核对口径

每个数字至少能回答：

- 测的是什么指标，如何定义？
- 基线是什么，是否在相同数据、模型、预算和硬件条件下比较？
- 样本量多大，来自受控样本还是实际业务？
- 数据属于哪个版本、哪个时间段？
- 哪份报告或记录能支持它？
- 是个人模块的结果，还是团队整体结果？

例如从 71.4% 到 82.5%，绝对变化是 **11.1 个百分点**；不能不加区分地写成“提升 11.1%”。没有必要计算相对增幅时，直接写前后值最清楚。

### 7.2 没有指标也可以写结果

可以写实际交付与验证结论，例如：

- 完成某模块并接入既有业务流程。
- 通过故障注入验证恢复能力。
- 在明确测试场景中拦截重复请求或非法状态迁移。
- 交付可复现脚本、部署流程或验收文档。

避免用“显著提升、大幅降低、行业领先”替代证据。测试通过只能支持其覆盖的机制，不能直接推导出生产可靠性、模型准确率或业务收益。

### 7.3 不夸大职责、状态与时间

- 已实现、已测试、已部署、已上线使用、已验证业务收益，分别表述。
- 不把计划中的优化写成已完成，不把候选版本写成已发布版本。
- 开源复现、二次开发与原创工作明确区分；重点写自己的增量贡献。
- 不把后续个人改进包装成过去实习期间的交付；时间跨度应覆盖所描述的实际工作。
- 不为了 STAR 结构虚构困难、职责、数字、用户量或结果。
- 尊重保密要求，不暴露内部仓库、客户信息、凭据与敏感业务指标。

## 8. 技术经历改写示例（仅示范表达）

### 8.1 从技术名词到问题解决

原句：

> 实现了 Agent 自进化，使用数据库、评测和版本管理。

按 STAR 梳理：

- S：候选生成与版本发布缺乏统一控制，存在未经充分验证就影响后续任务的风险。
- T：负责候选治理流程，使版本变更可验证、可审批、可回滚。
- A：设计候选状态机，串联评测、人工审批和影子验证，引入版本并发校验与审计。
- R：形成可追溯的发布流程，并通过对应测试验证非法阶段迁移被拒绝。

压缩后的写法：

> 针对候选版本缺少统一发布约束的问题，设计 Prompt/Skill 候选状态机，串联评测、人工审批与影子验证，结合版本并发校验和审计，实现受控发布与回滚，并验证非法阶段迁移被拦截。

使用限制：只有确实承担过上述工作、具备相应测试证据时才能使用。该示例不额外声称模型检测效果提升。

### 8.2 实习中的模块贡献

原句：

> 参与知识库开发，使用了 RAG 和向量数据库。

待填事实版本：

> 针对【实际业务】中【检索问题】，负责【真实模块范围】，实现【清洗/分块/检索/重排中的实际行动】，在【评测集与口径】下取得【已验证结果】，交付【具体产物】。

方括号必须由真实经历填充，不能把模板当成完成事实。

## 9. 从简历扩展到面试

简历用于压缩信息，面试用于解释细节。围绕同一条经历准备：

```text
S：当时的场景和主要问题是什么？
T：我负责什么，成功标准是什么？
A：我如何定位问题、选择方案、实施并处理困难？
R：最终结果如何，证据是什么，尚有哪些限制？
补充：如果重做，我会改进什么？
```

背景不必过长，重点展开个人行动、选择理由与结果验证。需要能够回答：为什么不用另一方案？最难的部分是什么？哪个环节是自己完成的？如何复现指标？结果不好时怎么办？

## 10. 提交前检查清单

- [ ] 有清楚的业务或技术问题，不只是技术栈罗列。
- [ ] 能区分项目整体目标与个人承担的职责。
- [ ] 行动包含具体机制或方法，能解释选择理由。
- [ ] 结果与行动有关联，有对应证据或具体交付物。
- [ ] 数字有基线、口径、样本范围和来源；百分比与百分点未混淆。
- [ ] 没有将受控测试结果表述为真实生产收益。
- [ ] 没有将开源原有能力、团队成果全部归为个人贡献。
- [ ] 时间、角色、完成状态与实际经历一致。
- [ ] 未验证的数据已删除或标为待核实，不擅自补数。
- [ ] 每条重点明确，背景不重复、技术名词不过度堆砌。
- [ ] 能对每条经历展开面试讲述，并承认真实限制。
- [ ] 输出格式符合现有简历模板，不随意修改未要求调整的部分。

## 11. 后续改写时可直接使用的提示词

```text
请参照《STAR法则_项目与实习经历编写指南.md》改写以下经历。

要求：
1. 先从材料中区分情境、个人任务、具体行动与结果。
2. 项目简介集中交代背景和目标，亮点重点写行动与结果，不必显式列出 S/T/A/R。
3. 突出我的实际贡献，区分开源已有能力、团队成果和个人改进。
4. 不编造指标、规模、角色、时间、上线状态或业务收益。
5. 证据不足时列出待确认问题，或采用不含虚构指标的交付描述。
6. 只修改指定部分，保留其他内容与原有 Markdown/LaTeX 格式。
7. 提供可直接使用的版本，并单独指出仍需核实的事实。

目标岗位：
经历类型：项目 / 实习
保留的原始格式：
需要修改的范围：
原始经历：
个人负责部分：
可用证据与指标口径：
篇幅限制：
```
